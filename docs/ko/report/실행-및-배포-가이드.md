# 운영 및 배포 가이드

## 적용범위
- 데스크톱에서 처음 사용
- Service 버전은 독립적으로 실행됩니다.
- Docker 배포
- macOS 첫 번째 출시

## 빠른 시작
1. 데스크탑을 시작하고 "서비스 시작"을 클릭하십시오.
2. "계정 관리"에 들어가서 계정을 추가하고 인증을 완료하세요.
3. 콜백이 실패하면 콜백 링크를 붙여넣어 수동으로 구문 분석을 완료합니다.
4. 사용량을 새로 고치고 계정 상태를 확인하세요.

## ccswitch를 통한 연결
ccswitch 또는 Codex CLI에서 CodexManager를 사용하려면 Codex의 ChatGPT 로그인을 유지하고 플랫폼 Key는 `config.toml`에만 설정하세요.

1. 대상 Codex 프로필에서 `codex login`을 실행하고 ChatGPT 계정으로 로그인합니다. 사용자 지정 `CODEX_HOME`을 사용하면 Codex 로그인과 CodexManager가 같은 디렉터리를 가리켜야 합니다.
2. 로그인으로 생성된 `auth.json`의 `auth_mode`가 `chatgpt`이고 `tokens.id_token`, `tokens.access_token`, `tokens.refresh_token`이 모두 비어 있지 않은 문자열인지 확인합니다. 토큰은 Codex가 생성하도록 하세요.
3. `Platform Keys`에서 일반 Key를 생성합니다.
4. Codex 연결 페이지에서 `CodexManager 사용`을 적용하거나 ccswitch에서 아래 예시처럼 `config.toml`만 업데이트합니다. 플랫폼 Key를 `experimental_bearer_token`에 넣고 ccswitch가 `auth.json`을 API Key 모드로 덮어쓰지 않는지 확인하세요.
5. 설정을 적용한 뒤 Codex CLI를 다시 시작합니다.

일반 경로:

- macOS / Linux: `~/.codex/auth.json`, `~/.codex/config.toml`
- Windows: `%USERPROFILE%\.codex\auth.json`, `%USERPROFILE%\.codex\config.toml`

로그인 후 `auth.json` 구조 예시(Codex가 생성한 실제 파일을 유지하세요):

```json
{
  "auth_mode": "chatgpt",
  "tokens": {
    "id_token": "non_empty_value_generated_by_codex_login",
    "access_token": "non_empty_value_generated_by_codex_login",
    "refresh_token": "non_empty_value_generated_by_codex_login"
  }
}
```

- 게이트웨이 설정은 `auth.json`을 바이트 단위로 유지하고 플랫폼 Key를 `config.toml`에만 기록합니다. CodexManager 시작 시에도 `auth.json`을 기록하지 않습니다.
- ChatGPT 로그인이 없거나 로그인 모드가 다르거나 필수 토큰이 누락/빈 값이면 게이트웨이 설정을 적용하지 않고 `auth.json`과 `config.toml`을 유지합니다. 인증 파일도 생성하지 않습니다.
- 게이트웨이 provider는 항상 `name = "cm"`, `requires_openai_auth = true`를 사용하며 이 필드를 제거하는 스위치는 없습니다.

`config.toml` 예시:

```toml
model = "gpt-6-sol"
model_provider = "cm"
review_model = "gpt-6-sol"
approval_policy = "on-request"
sandbox_mode = "workspace-write"
cli_auth_credentials_store = "file"
service_tier = "fast"

[model_providers.cm]
name = "cm"
base_url = "http://localhost:48760/v1"
wire_api = "responses"
requires_openai_auth = true
experimental_bearer_token = "replace_with_codexmanager_platform_key"
supports_websockets = true
```

- Settings에서 service port를 바꿨다면 `base_url`의 `48760`도 같이 바꾸세요.
- Docker / Web 모드에서는 컨테이너 내부 주소 대신 브라우저로 접근 가능한 Web 주소에 `/v1`을 붙여 사용하세요(예: `http://10.10.121.253:48761/v1`).

## 계정 가져오기 및 내보내기
- `批量导入`: 여러 개의 `.json/.txt` 파일을 선택하여 함께 가져옵니다.
- `按文件夹导入`: 데스크톱에서만 사용할 수 있습니다. 디렉터리를 선택한 후 `.json` 파일을 재귀적으로 스캔하여 일괄적으로 가져옵니다. 빈 파일은 자동으로 건너뜁니다.
- `导出用户`: 디렉터리를 선택한 후 "계정당 하나의 JSON 파일"을 클릭하여 내보내 백업 및 마이그레이션을 용이하게 합니다.

## Service 버전
1. 릴리스에서 `CodexManager-service-<platform>.zip`을 다운로드하고 압축을 풉니다.
2. `codexmanager-start`을 시작하는 것이 좋습니다. 프로세스는 서비스 + 웹을 시작하고 콘솔 `Ctrl+C`에서 직접 닫을 수 있습니다.
3. `codexmanager-web`을 실행하면 동일한 디렉토리에 자동으로 `codexmanager-service`이 표시되고 브라우저가 열립니다.
4. 또는 `codexmanager-service`을 먼저 시작한 다음 `codexmanager-web`을 시작하십시오.
5. 기본 주소: 서비스 `localhost:48760`, Web UI `http://localhost:48761/`.
6. 닫기: `http://localhost:48761/__quit`을 방문하세요. 웹 서비스가 자동으로 시작된 경우 함께 닫으려고 시도합니다.
7. 직접 역방향 프록시를 수행하거나 프런트엔드 정적 리소스를 분할 배포해야 하는 경우 `/api/runtime` 및 `/api/rpc`을 동시에 전달해야 합니다. 정적 파일만 호스팅하면 관리 페이지가 제대로 작동하지 않습니다.

## Docker 배포

### GitHub 패키지/GHCR
- 릴리스가 출시된 후 `codexmanager-service` 및 `codexmanager-web` 이미지가 GitHub 패키지(GHCR)에 동시에 푸시됩니다.
- 정식 릴리스는 버전 태그와 `stable`, `latest` 태그를 함께 갱신합니다. 프리릴리스는 버전 태그만 게시하며 부동 태그를 덮어쓰지 않습니다.
- 자동 업데이트에는 `stable`을 사용하고, 버전을 고정하려면 `docker pull ghcr.io/qxcnm/codexmanager-service:v0.6.0`처럼 버전 태그를 사용하세요.
- [`docker/docker-compose.release.yml`](../../../docker/docker-compose.release.yml)은 기본적으로 `stable`을 사용합니다. 버전을 고정할 때만 `CODEXMANAGER_RELEASE_TAG`을 설정하세요.
- 예: `CODEXMANAGER_RELEASE_TAG=v0.6.0 docker compose -f docker/docker-compose.release.yml up -d`
- `registry.cn-hangzhou.aliyuncs.com/kilimiao/codex-manager`는 현재 공식 릴리스 워크플로에 포함되지 않아 버전이 뒤처질 수 있습니다. 공식적으로 유지되는 사전 빌드 이미지는 위 GHCR의 `service` 및 `web` 이미지입니다.

### 선택 사항: Docker OTA 업데이트

- 공식 Release Compose에는 Watchtower OTA 검사 sidecar가 선택적으로 포함되어 있습니다. `CODEXMANAGER_RELEASE_TAG`을 이동하는 `stable` 태그로 두고 다음을 실행하세요.

  ```bash
  docker compose -f docker/docker-compose.release.yml --profile ota up -d
  ```

- Watchtower는 300초마다 업데이트 표시가 붙은 CodexManager service/web 이미지를 확인하지만 `ota` profile은 사용 가능한 업데이트만 보고하고 컨테이너를 교체하지 않습니다. `CODEXMANAGER_OTA_INTERVAL=60`으로 주기를 바꿀 수 있습니다.
- 사용자가 승인한 후 다음 명령을 한 번 실행하면 새 이미지를 받고 순차적으로 재시작합니다.

  ```bash
  docker compose -f docker/docker-compose.release.yml --profile ota run --rm --no-deps codexmanager-ota --label-enable --run-once --cleanup --rolling-restart --stop-timeout 20s
  ```

- 사용자가 자동 확인 및 업그레이드에 명시적으로 동의한 경우에만 `ota-auto` profile을 사용하세요.

  ```bash
  docker compose -f docker/docker-compose.release.yml --profile ota-auto up -d
  ```

- `CODEXMANAGER_RELEASE_TAG=v0.6.2`처럼 버전을 고정하면 다른 릴리스로 자동 이동하지 않습니다. OTA sidecar는 Docker socket 접근 권한이 필요하므로 신뢰할 수 있는 호스트에서만 활성화하세요.
- service가 재시작될 때 같은 `/data` 볼륨을 사용해 자동 마이그레이션을 수행합니다. 업그레이드 중에는 해당 볼륨을 삭제하지 마세요.

### 방법 1: docker compose
```bash
docker compose -f docker/docker-compose.yml up --build
```

브라우저 열기: `http://localhost:48761/`

### 방법 2: 별도로 빌드하고 실행
```bash
#서비스
docker build -f docker/Dockerfile.service -t codexmanager-service .
docker network create codexmanager-net

docker run --rm --name codexmanager-service \
  --network codexmanager-net \
  --network-alias codexmanager-service \
  -p 48760:48760 \
  -v codexmanager-data:/data \
  -e CODEXMANAGER_RPC_TOKEN=replace_with_your_token \
  codexmanager-service

# 웹 (컨테이너끼리는 호스트 포트가 아니라 Docker 네트워크 주소를 사용)
docker build -f docker/Dockerfile.web -t codexmanager-web .
docker run --rm --name codexmanager-web \
  --network codexmanager-net \
  -p 48761:48761 \
  -v codexmanager-data:/data \
  -e CODEXMANAGER_WEB_NO_SPAWN_SERVICE=1 \
  -e CODEXMANAGER_SERVICE_ADDR=codexmanager-service:48760 \
  -e CODEXMANAGER_RPC_TOKEN=replace_with_your_token \
  codexmanager-web
```

- 참고: Web 비밀번호, 설정 항목, 캐시 모델 목록 및 기타 상태가 서비스와 일치하도록 하려면 `codexmanager-web` 및 `codexmanager-service`이 동일한 `/data` 볼륨을 공유해야 합니다.
- Linux 에서 컨테이너가 호스트 포트로 직접 접근해야 한다면 `--add-host=host.docker.internal:host-gateway` 를 추가해야 합니다. 그렇지 않으면 `host.docker.internal` 이 해석되지 않는 경우가 많습니다.

## macOS 첫 시작
- 현재 macOS 릴리스 제품은 Apple 개발자 계정을 사용하여 공증되지 않았으므로 브라우저에서 처음 다운로드한 후 Gatekeeper에서 "손상됨" 메시지를 표시하거나 열기를 거부할 수 있습니다.
- macOS `dmg` 릴리스에는 `Open CodexManager.command` 및 `README-macOS-first-launch.txt`이 내장되어 있습니다.
- 먼저 `CodexManager.app`을 "애플리케이션"으로 드래그한 후 스크립트를 더블클릭하여 첫 번째 릴리스를 완료하는 것이 좋습니다.
- 직접 실행할 수도 있습니다.

```bash
xattr -dr com.apple.quarantine /Applications/CodexManager.app
```

- 그래도 차단되어 있는 경우 `CodexManager.app` 항목을 다시 "우클릭 -> 열기"를 실행해 주세요.
